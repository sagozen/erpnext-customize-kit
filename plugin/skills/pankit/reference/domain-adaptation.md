# Adapt the kit to another industry

Use only when the active business domain changes. Do not carry curtain formulas, terminology, role assumptions or app names into a new customer silently.

1. Record industry, customer, app namespace, outcome, constraints, non-goals and acceptance. Preserve framework guidance and delivery commands.
2. Gather actual transaction examples, catalog, units, pricing, procurement/production method, approvals, reports and exceptions. Name the human owner for each unanswered rule.
3. Create a domain contract under the customer's docs with glossary, process map, fit-gap, data dictionary, calculations with independent worked examples, role matrix, revision policy and UAT scenarios.
4. Select that contract explicitly in project instructions. For this project use sankaku_erp unless the user chooses another namespace. Do not create a generic plugin engine or a domain-selection CLI merely to support one new industry.
5. Read the active domain contract instead of curtain-domain.md. Recheck standard ERPNext fit and installed-version APIs. Test at least one ordinary transaction, one exception, unauthorized access and migration replay.
6. Migrate historical business records only under a separate data migration plan; changing agent guidance does not change deployed schema or records.

Acceptance: new-industry requests no longer assume windows, fabric fullness or curtain units; shared ERPNext permissions, lifecycle, version and recovery checks remain intact. Update routing examples and beginner documentation when distributing a distinct kit.
